3. KOMPLEXA TABELLER (med join / merge-tabell) — Observation KOLUMNLAYOUT
--------------------------------------------------------------------------------
3.1  Views/Observation/Index.cshtml        rad 20–55       
     KOLUMNLAYOUT (kravspec: "kolumnlayout när kolumnlayout efterfrågas").
     Yttre loop: foreach (var obsRow in ViewBag.ObsTable.Rows) — en rad per unik IncidentId.
     Inre loop: foreach (var obsInnerRow in ViewBag.ObsTable.Rows) where IncidentId matchar.
     Nästlad tabell i kolumn 3: visar alla observationer för den incidenten (ObsId, Datum, Säkerhet, Grad, Handläggare, Arkivera-länk).
     Logik: string prev = "None"; if (prev != obsRow["IncidentId"]) { ny yttre rad } prev = obsRow["IncidentId"].

3.2  Views/Observation/Index.cshtml        rad 26–52       
     Detaljerad logik: 
     - Rad 26: prev = "None" initieras före loop.
     - Rad 31: if (prev != obsRow["IncidentId"].ToString()) — ny incident.
     - Rad 33–34: Skriver IncidentNamn och PlatsNamn i första två celler.
     - Rad 35–50: Inre loop som filtrerar på samma IncidentId, bygger <table> i tredje cellen.
     - Rad 52: prev = obsRow["IncidentId"].ToString() uppdateras.

3.3  Models/ObservationModel.cs            rad 17–27       
     GetObservationsWithDetails(): 
     SQL: "SELECT o.IncidentId, o.IncidentNamn, p.PlatsNamn, o.ObsId, o.Datum, o.Sakerhet, g.Beskrivning AS Grad, CONCAT(a.Fornamn, ' ', a.Efternamn) AS Handlaggare 
           FROM Observation o 
           JOIN Plats p ON o.PlatsKod = p.PlatsKod 
           JOIN GradBeskrivning g ON o.GradKod = g.GradKod 
           JOIN Agent a ON o.RegistreradAvNamn = a.AgentNamn AND o.RegistreradAvNr = a.AgentNr 
           ORDER BY o.IncidentId, o.ObsId;"
     JOIN 4 tabeller: Observation (merge-tabell med IncidentNamn), Plats, GradBeskrivning, Agent.
     ORDER BY IncidentId, ObsId avgörande för kolumnlayout-logiken i vyn.

3.4  Controllers/ObservationController.cs  rad 18–24       
     Index(): Hämtar tre ViewBag-värden:
     - ObsTable = GetObservationsWithDetails() (för kolumnlayout)
     - AllPlats = GetAllPlats() (för dropdown i filtrera + insert)
     - AllHandlaggare = GetAllHandlaggare() (för 2 dropdownar i insert)

5.1  Views/Observation/Index.cshtml        rad 58–93       
     Formulär: method="post" action="@Url.Action("InsertObservation", "Observation")"
     Fält: ObsId (text), Incidentnr (text), Incidentnamn (text), 
     Dropdown Plats (från ViewBag.AllPlats), 
     Grad (number min=1 max=4), Säkerhet (number step=0.01 min=1 max=114),
     VIKTIGT — 2 dropdownar för Handläggare:
       - regnamn: <select name="regnamn"> fylls från ViewBag.AllHandlaggare (AgentNamn + Namn)
       - regnr:   <select name="regnr">   fylls från ViewBag.AllHandlaggare (AgentNr + Namn)
     Varför 2? Handläggare har sammansatt PK (AgentNamn, AgentNr) — båda krävs för FK.
     Submit "Add".

5.2  Controllers/ObservationController.cs  rad 32–36       
     InsertObservation(string obsid, incidentid, incidentnamn, platskod, gradkod, sakerhet, regnamn, regnr):
     Alla parametrar strängar från formuläret.
     _observationModel.InsertObservation(obsid, incidentid, incidentnamn, platskod, gradkod, sakerhet, regnamn, regnr);
     RedirectToAction("Index") — PRG-mönster (Post-Redirect-Get) förhindrar dubbelpost vid refresh.

5.3  Models/ObservationModel.cs            rad 53–69       
     InsertObservation(8 parametrar):
     SQL: "INSERT INTO Observation(ObsId, Datum, GradKod, Sakerhet, IncidentId, IncidentNamn, PlatsKod, RegistreradAvNamn, RegistreradAvNr) 
           VALUES(@OBSID, NOW(), @GRAD, @SAKERHET, @INCID, @INCNAMN, @PLATS, @REGNAMN, @REGNR);"
     Datum sätts av databasen med NOW() — ingen tid från klienten.
     Alla 9 värden via Parameters.AddWithValue — skydd mot SQL-injection.
     ExecuteNonQuery() → stänger connection.

7.3  Models/ObservationModel.cs            rad 83–91       
     ArkiveraObservation(string obsid):
     SQL: "CALL ARKIVERAOBSERVATION(@OBSID);"
     MySqlCommand med Parameters.AddWithValue("@OBSID", obsid).
     ExecuteNonQuery().

7.4  database.sql                          rad 251–259     
     CREATE PROCEDURE ARKIVERAOBSERVATION(IN p_ObsId INTEGER)
     BEGIN
       DELETE FROM Rapporterat WHERE ObsId = p_ObsId;           -- Steg 1: Rensa FK-kopplingar (Person→Obs)
       INSERT INTO ARKIVERADObservation SELECT * FROM Observation WHERE ObsId = p_ObsId;  -- Steg 2: Kopiera till arkiv
       DELETE FROM Observation WHERE ObsId = p_ObsId;           -- Steg 3: Radera original
     END;
     ATOMÄRT: Om något steg misslyckas rullas allt tillbaka (transaktion implicit i procedur).
     Används i BÅDE PHP (rad 85: CALL ARKIVERAOBSERVATION(?)) och .NET — DRY.

10. DESIGNVAL — MOTIVERINGAR (personliga frågor)
--------------------------------------------------------------------------------
10.1 Varför SchoolConnection?              
     Fil: Models/*Model.cs rad 14
     Svar: "Skolans miljövariabel heter 'SchoolConnection'. Om jag använde 'ConnectionString' 
     så skulle standardkonfigurationen krocka. Jag läser config["SchoolConnection"] i konstruktorn."

10.2 Varför 2 dropdownar Handläggare?      
     Fil: Views/Observation/Index.cshtml rad 74–91
     Svar: "Handläggare har sammansatt primärnyckel (AgentNamn CHAR(1), AgentNr INTEGER). 
     För att sätta FK i Observation (RegistreradAvNamn, RegistreradAvNr) måste båda värden väljas. 
     Därför två dropdownar: en för namn, en för nummer."

10.3 Varför kolumnlayout .NET, radlayout PHP?
     Svar: ".NET: En incident har N observationer (1:N). Kravspec: 'kolumnlayout när kolumnlayout efterfrågas'. 
     Yttre rad = incident, inre tabell = observationer i kolumn 3.
     PHP: En observation har N vittner (1:N via Rapporterat). Radlayout: yttre rad = observation, 
     inre tabell = vittner i kolumn 8. Olika relationer → olika layout."

10.4 Varför procedur för arkivering?       
     Fil: database.sql rad 251–259
     Svar: "Tre steg måste ske atomärt: 1) Radera FK-rader i Rapporterat, 2) Kopiera till ARKIVERADObservation, 3) Radera från Observation. 
     Om steg 2 misslyckas ska inte steg 3 köras. Procedur garanterar all-eller-ingen. 
     Används i båda applikationer — DRY."

10.5 MVC-kedja förklaring                  
     Svar: "Varje funktion följer View → Controller → Model → SQL. 
     View: formulär/länk skickar data. Controller: tar emot, anropar modell, redirect. 
     Model: öppnar connection, kör parametriserad SQL, returnerar DataTable/void. 
     SQL: körs i databasen. Alla 6 funktioner har denna kedja (se block 11)."
