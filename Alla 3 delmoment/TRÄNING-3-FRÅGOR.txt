VAD DU SÄGER (manus — läs inte, tala fritt)
-------------------------------------------
"Här är min komplexa tabell för PHP. Den visar observationer med vittnen — en
observation kan ha flera vittner (1:N), därför valde jag RADLAYOUT.

Koden börjar rad 168. Nyckeln är jämförelsevariabeln $prevObs rad 182.

FÖRKLARING RAD FÖR RAD:
- Rad 183: SQL med LEFT JOIN Observation → Rapporterat → Person + JOIN Plats.
  Sorterat på ObsId så samma observation kommer i följd.
- Rad 185-186: Loopen kör varje rad från frågan.
- Rad 186-188: Om $prevObs != nuvarande ObsId → ny observation.
  Stänger föregående inre tabell (</table></td></tr>) om inte första.
- Rad 190-197: Skriver yttre radens celler (ObsId, Datum, Grad, Säkerhet,
  Incident, Plats, Handläggare) — sedan öppnar <td><table> för vittnerna.
- Rad 198-199: Header i inre tabell (PersonId, Namn, Kodnamn).
- Rad 201-206: Om PersonId finns (inte NULL) → skriv en rad i inre tabell.
- Rad 208: Uppdatera $prevObs = nuvarande ObsId.
- Rad 210-212: Efter loopen stänger sista inre tabell.

VARFÖR RADLAYOUT HÄR?
En observation har N vittner → vittnerna hör till ENA observationen.
De visas som en nästlad tabell INNE I observationens rad (kolumn 8).
Detta är radlayout: yttre loop = observationer, inre loop = vittner per observation."

NYCKELORD ATT NÄMNA: "LEFT JOIN", "jämförelsevariabel $prevObs", "nä stlad tabell", "1:N relation"

VAD DU SÄGER — DELETE / ARKIVERA (manus)
----------------------------------------
"DELETE görs via arkivering — en lagrad procedur som är atomär.

VIEW (Index.cshtml:46):
@Html.ActionLink skapar länk: /Observation/ArkiveraObservation?obsid=501
GET-request (länk) → anropar action direkt.

CONTROLLER (ObservationController.cs:44-48):
Tar obsid, anropar modell.ArkiveraObservation(obsid), redirect Index.

MODEL (ObservationModel.cs:83-91):
SQL: 'CALL ARKIVERAOBSERVATION(@OBSID);'
Parameter @OBSID via AddWithValue.
ExecuteNonQuery.

DATABASE.SQL (Procedur, rad 251-259):
CREATE PROCEDURE ARKIVERAOBSERVATION(IN p_ObsId INTEGER)
BEGIN
  DELETE FROM Rapporterat WHERE ObsId = p_ObsId;     -- 1. Rensa FK-kopplingar
  INSERT INTO ARKIVERADObservation SELECT * FROM Observation WHERE ObsId = p_ObsId;  -- 2. Kopiera
  DELETE FROM Observation WHERE ObsId = p_ObsId;     -- 3. Radera original
END;

VARFÖR PROCEDUR? Atomärt — antingen alla tre steg lyckas, eller inget.
Används i BÅDE PHP (CALL) och .NET (CALL) — DRY-princip."

NYCKELORD ATT NÄMNA: "MVC-kedja", "Parameters.AddWithValue", "PRG-mönster", "atomär procedur", "FK-kopplingar rensas först"

================================================================================

VAD DU VISAR PÅ GIT.WEBUG.SE — database.sql

RAD 63-70  ← Öppna hit, visa hela blocket

ANDRA BRA EXEMPEL:

- Plats UNIQUE på PlatsNamn                rad 41
- FK från Observation till Handlaggare     rad 68

VAD DU SÄGER — MANUS (för Observation CHECK + FK)
-------------------------------------------------
"Här är Observation-tabellen, rad 53-71. Jag visar constraints på rad 63-70.

PRIMARY KEY (rad 63):
ObsId är PK — unikt ID för varje observation.

CHECK 1 (rad 64-65):
'CHECK (GradKod >= 1 AND GradKod <= 4)'
Syfte: Domänintegritet — närkontaktsgrad enbart 1-4.
Fungerar även om FK till GradBeskrivning inaktiveras.
Dubbelsäkerhet tillsammans med triggern CHECKOBSGRAD (BEFORE INSERT).

CHECK 2 (rad 66-67):
'CHECK (Sakerhet >= 1.00 AND Sakerhet <= 114.00)'
Syfte: Säkerhet i procent måste vara 1-114%.
Fångar felaktiga värden vid INSERT/UPDATE direkt i databasen.

FK 1 (rad 68):
'FOREIGN KEY (RegistreradAvNamn, RegistreradAvNr)
 REFERENCES Handlaggare(AgentNamn, AgentNr)'
Syfte: Referensintegritet — bara handläggare får registrera.
Sammansatt FK matchar sammansatt PK i Handlaggare.

FK 2 (rad 69):
'FOREIGN KEY (PlatsKod) REFERENCES Plats(PlatsKod)'
Syfte: Endast kända platser från kodtabell Plats.

FK 3 (rad 70):
'FOREIGN KEY (GradKod) REFERENCES GradBeskrivning(GradKod)'
Syfte: Endast kända grader från kodtabell GradBeskrivning.

SAMMANFATTNING:
CHECK = domänregler (värden), FK = referensregler (kopplingar).
Båda körs av databasen — skyddar även om applikationen glömmer validera."

NYCKELORD ATT NÄMNA: "domänintegritet", "referensintegritet", "dubbelsäkerhet med trigger", "sammansatt FK"
