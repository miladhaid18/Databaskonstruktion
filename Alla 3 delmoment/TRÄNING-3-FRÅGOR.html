"Här är min komplexa tabell för PHP. Den visar observationer med vittnen — en observation kan ha flera vittner (1:N), därför valde jag RADLAYOUT.

Koden börjar rad 168. Nyckeln är jämförelsevariabeln $prevObs rad 182.

Rad 198–199: Header i inre tabell (PersonId, Namn, Kodnamn).

Rad 210–212: Efter loopen stänger sista inre tabell.

Varför radlayout här? En observation har N vittner → vittnerna hör till ENA observationen. De visas som en nästlad tabell INNE I observationens rad (kolumn 8). Yttre loop = observationer, inre loop = vittner per observation."

Manus — UPDATE

"Här är UPDATE-kedjan — fyra filer: View → Controller → Model → SQL.

VIEW (Index.cshtml:96–109): Dropdown hämtar alla observationer från ViewBag.ObsTable. Användaren väljer ObsId och fyller i ny Säkerhet. POST till UpdateSakerhet-action.

CONTROLLER (ObservationController.cs:38–42): Tar obsid och sakerhet som strängar. Anropar _observationModel.UpdateSakerhet(obsid, sakerhet). Redirect till Index (PRG-mönster).

MODEL (ObservationModel.cs:71–81): Öppnar connection med SchoolConnection från appsettings.json. SQL: UPDATE Observation SET Sakerhet = @SAKERHET WHERE ObsId = @OBSID; Parameters.AddWithValue för BÅDA — ingen strängkonkatenering, skydd mot injection. ExecuteNonQuery → stänger connection.

SQL: Enkel UPDATE på primärnyckel ObsId. Snabbt, säkert."

Manus — DELETE / ARKIVERA

"DELETE görs via arkivering — en lagrad procedur som är atomär.

VIEW (Index.cshtml:46): @Html.ActionLink skapar länk: /Observation/ArkiveraObservation?obsid=501. GET-request → anropar action direkt.

CONTROLLER (ObservationController.cs:44–48): Tar obsid, anropar modell.ArkiveraObservation(obsid), redirect Index.

MODEL (ObservationModel.cs:83–91): SQL: CALL ARKIVERAOBSERVATION(@OBSID); Parameter @OBSID via AddWithValue. ExecuteNonQuery.

DATABASE.SQL (Procedur, rad 251–259):
CREATE PROCEDURE ARKIVERAOBSERVATION(IN p_ObsId INTEGER)
BEGIN
DELETE FROM Rapporterat WHERE ObsId = p_ObsId; -- 1. Rensa FK-kopplingar
INSERT INTO ARKIVERADObservation SELECT * FROM Observation WHERE ObsId = p_ObsId; -- 2. Kopiera
DELETE FROM Observation WHERE ObsId = p_ObsId; -- 3. Radera original
END;
Varför procedur? Atomärt — antingen alla tre steg lyckas, eller inget. Används i BÅDE PHP (CALL) och .NET (CALL) — DRY-princip."
NYCKELORD ATT NÄMNA: MVC-kedja Parameters.AddWithValue PRG-mönster atomär procedur FK-kopplingar rensas först DRY-princip

Manus — Observation-tabell (rad 63–70)


PRIMARY KEY (rad 63): ObsId är PK — unikt ID för varje observation.

CHECK 1 (rad 64–65): CHECK (GradKod >= 1 AND GradKod <= 4)
Syfte: Domänintegritet — närkontaktsgrad enbart 1–4. Fungerar även om FK till GradBeskrivning inaktiveras. Dubbelsäkerhet tillsammans med triggern CHECKOBSGRAD (BEFORE INSERT).

CHECK 2 (rad 66–67): CHECK (Sakerhet >= 1.00 AND Sakerhet <= 114.00)
Syfte: Säkerhet i procent måste vara 1–114%. Fångar felaktiga värden vid INSERT/UPDATE direkt i databasen.

FK 1 (rad 68): FOREIGN KEY (RegistreradAvNamn, RegistreradAvNr) REFERENCES Handlaggare(AgentNamn, AgentNr)
Syfte: Referensintegritet — bara handläggare får registrera. Sammansatt FK matchar sammansatt PK i Handlaggare.

FK 2 (rad 69): FOREIGN KEY (PlatsKod) REFERENCES Plats(PlatsKod) — Endast kända platser från kodtabell.

FK 3 (rad 70): FOREIGN KEY (GradKod) REFERENCES GradBeskrivning(GradKod) — Endast kända grader från kodtabell.

Sammanfattning: CHECK = domänregler (värden), FK = referensregler (kopplingar). Båda körs av databasen — skyddar även om applikationen glömmer validera."
NYCKELORD ATT NÄMNA: domänintegritet referensintegritet dubbelsäkerhet med trigger sammansatt FK
