Del 1 – databasen rad för rad

Alla exempel är från din database.sql (260 rader). Vi hoppar över upprepade rader och förklarar mönstren en gång.

Så läser du varje rad

  1. Typ: skapar struktur, skriver data, läser, ändrar, ger rättighet, kör automatiskt?
  2. Objekt: vilken tabell/kolumn/parameter?
  3. Varför: vilken regel eller vilket krav uppfylls?
  4. Koppling: vilken annan tabell/app-del hör den ihop med?
Läs högt: "Den här raden [gör X] på [tabell] därför att [regel]."

1. Rad 1–3: skapa en fräsch databas

1  DROP DATABASE IF EXISTS a25milha;
2  CREATE DATABASE a25milha;
3  USE a25milha;
RadVad den gör
1Tar bort databasen om den finns. Gör filen körbar flera gånger utan "already exists". Destruktivt – all data försvinner.
2Skapar en tom databas med namnet a25milha.
3Väljer databasen så att alla följande CREATE TABLE hamnar i den.

2. Agent (rad 9–20): tabell med sammansatt primärnyckel och CHECK

9   CREATE TABLE Agent(
10    AgentNamn CHAR(1) NOT NULL,
11    AgentNr INTEGER NOT NULL,
12    Fornamn VARCHAR(50) NOT NULL,
13    Efternamn VARCHAR(50) NOT NULL,
14    Lon INTEGER DEFAULT 13000,
15    PRIMARY KEY (AgentNamn, AgentNr),
16    /* Restriktion: Lonen maste ligga mellan 12000 och 25000 kr for handlaggare */
17    CHECK (Lon >= 12000 AND Lon <= 25000),
18    /* Restriktion: Agentnumret maste vara mellan 1 och 99 */
19    CHECK (AgentNr > 0 AND AgentNr <= 99)
20  ) ENGINE=INNODB;
RadVad den gör
9Börjar skapa tabellen Agent. Varje rad = en agent.
10AgentNamn är en bokstavskod (J, K, A, L). CHAR(1) = alltid exakt ett tecken. NOT NULL = får inte saknas.
11AgentNr är ett heltal. Tillsammans med bokstaven identifierar det agenten.
12–13För- och efternamn som text upp till 50 tecken, obligatoriska.
14Lön som heltal. Om värdet utelämnas vid insert blir det 13000 (DEFAULT).
15Sammansatt primärnyckel: kombinationen (AgentNamn, AgentNr) är unik. Bokstaven ensam är inte unik, inte heller numret.
17CHECK = regel som databasen alltid kontrollerar: lönen måste vara 12 000–25 000.
19Agentnumret måste vara 1–99.
20ENGINE=INNODB = lagringsmotor som stödjer främmande nycklar och transaktioner.
Säg: "Agent har en sammansatt primärnyckel och två CHECK-constraints som skyddar lön och agentnummer."

3. AgentKommentar (rad 22–29): horisontell denormalisering

22  /* HORISONTELL DENORMALISERING: Utlyft av stor textkolumn (Kommentar) */
23  CREATE TABLE AgentKommentar(
24    AgentNamn CHAR(1) NOT NULL,
25    AgentNr INTEGER NOT NULL,
26    Kommentar VARCHAR(1024) NOT NULL,
27    PRIMARY KEY (AgentNamn, AgentNr),
28    FOREIGN KEY (AgentNamn, AgentNr) REFERENCES Agent(AgentNamn, AgentNr)
29  ) ENGINE=INNODB;
RadVad den gör
23Skapar en egen tabell för agentens stora textkommentar.
24–25Samma nyckel som Agent – det finns max en kommentar per agent (1:1).
26VARCHAR(1024) = upp till 1024 tecken. Stor text som inte behövs vid varje agentfråga.
27Primärnyckeln är samma par → ingen agent kan få två kommentarer.
28FOREIGN KEY → kommentaren kan inte finnas utan en agent. Referentiell integritet.

Varför: om kommentaren låg i Agent skulle varje agentrad bära upp till 1024 tecken i onödan. Nu är huvudtabellen liten och snabb; texten hämtas bara vid behov.

4. Handlaggare (rad 31–36): rolltabell (delmängd)

31  CREATE TABLE Handlaggare(
32    AgentNamn CHAR(1) NOT NULL,
33    AgentNr INTEGER NOT NULL,
34    PRIMARY KEY (AgentNamn, AgentNr),
35    FOREIGN KEY (AgentNamn, AgentNr) REFERENCES Agent(AgentNamn, AgentNr)
36  ) ENGINE=INNODB;
RadVad den gör
31Tabell för de agenter som också är handläggare.
32–34Samma nyckel som Agent; primärnyckeln gör att en agent bara kan registreras en gång som handläggare.
35FK till Agent: en handläggare måste vara en befintlig agent.

Varför: alla handläggare är agenter, men alla agenter är inte handläggare. Att raden finns i Handlaggare är själva rollen. Testdatan visar det: agent L finns i Agent men inte i Handlaggare.

5. Plats (38–43) och GradBeskrivning (45–50): kodtabeller

38  /* KODTABELL 1: Uppslagstabell för platser (Kodifiering 1) */
39  CREATE TABLE Plats(
40    PlatsKod INTEGER NOT NULL,
41    PlatsNamn VARCHAR(100) NOT NULL UNIQUE,
42    PRIMARY KEY (PlatsKod)
43  ) ENGINE=INNODB;

45  /* KODTABELL 2: Uppslagstabell för närkontaktsgrader (Kodifiering 2) */
46  CREATE TABLE GradBeskrivning(
47    GradKod INTEGER NOT NULL,
48    Beskrivning VARCHAR(100) NOT NULL,
49    PRIMARY KEY (GradKod)
50  ) ENGINE=INNODB;
RadVad den gör
39–43Plats kopplar en sifferkod till ett platsnamn. UNIQUE på namnet förhindrar två koder för samma plats.
46–50GradBeskrivning kopplar grad 1–4 till en förklaring. Används i apparnas dropdowns.

Kodifiering: i stället för att upprepa långa texter i varje observation sparar Observation bara PlatsKod och GradKod. Det sparar plats och gör ändringar enkla.

6. Observation (rad 52–71): merge + kodifiering + constraints

52  /* DENORMALISERAD TABELL 1 (AKTIVA OBSERVATIONER - MERGE + KODIFIERING 1 & 2) */
53  CREATE TABLE Observation(
54    ObsId INTEGER NOT NULL,
55    Datum DATETIME NOT NULL,
56    GradKod INTEGER NOT NULL,
57    Sakerhet DECIMAL(5,2) NOT NULL,
58    IncidentId INTEGER NOT NULL,
59    IncidentNamn VARCHAR(100) NOT NULL,
60    PlatsKod INTEGER NOT NULL,
61    RegistreradAvNamn CHAR(1) NOT NULL,
62    RegistreradAvNr INTEGER NOT NULL,
63    PRIMARY KEY (ObsId),
64    /* Restriktion: Narkontaktsgraden maste vara ett heltal fran 1 till 4 */
65    CHECK (GradKod >= 1 AND GradKod <= 4),
66    /* Restriktion: Sakerheten i procent maste vara mellan 1.00 och 114.00 */
67    CHECK (Sakerhet >= 1.00 AND Sakerhet <= 114.00),
68    FOREIGN KEY (RegistreradAvNamn, RegistreradAvNr) REFERENCES Handlaggare(AgentNamn, AgentNr),
69    FOREIGN KEY (PlatsKod) REFERENCES Plats(PlatsKod),
70    FOREIGN KEY (GradKod) REFERENCES GradBeskrivning(GradKod)
71  ) ENGINE=INNODB;
RadVad den gör
53–54Tabellen för aktiva observationer. ObsId är unikt för varje observation.
55DATETIME = datum + tid. NOW() i appen fyller i aktuell tid.
56GradKod = kod som pekar på GradBeskrivning.
57DECIMAL(5,2) = totalt 5 siffror, 2 decimaler (t.ex. 114.00). Exakt tal, inte flyttal.
58–59Incidentens id och namn ligger direkt i tabellen – det är merge: ingen separat Incident-tabell, färre joins.
60PlatsKod = kod som pekar på Plats.
61–62Vem som registrerade observationen, som ett sammansatt par.
63Primärnyckel på ObsId.
65Graden måste vara 1–4 (domänregel).
67Säkerheten måste vara 1.00–114.00.
68Sammansatt FK: registreraren måste finnas i Handlaggare.
69–70FK till Plats och GradBeskrivning – inga påhittade koder.

Varför både CHECK och trigger? CHECK är en deklarativ regel som alltid gäller. Triggern CHECKOBSGRAD ger dessutom ett tydligt felmeddelande. Dubbelt skydd är avsiktligt.

7. ARKIVERADObservation (rad 73–92): vertikal denormalisering

73  /* VERTIKAL DENORMALISERING: Tabell för arkiverade/mörklagda observationer */
74  CREATE TABLE ARKIVERADObservation(
75    ... samma kolumner och constraints som Observation ...
92  ) ENGINE=INNODB;

Tabellen har exakt samma kolumner som Observation (ObsId, Datum, GradKod, Sakerhet, IncidentId, IncidentNamn, PlatsKod, RegistreradAvNamn, RegistreradAvNr, PK, CHECK, FK). Därför hoppar vi över de upprepade raderna.

RadVad den gör
73Kommentaren säger syftet: arkiverade observationer.
74Egen tabell för gamla rader. Aktiv tabell hålls liten och snabb.
84–91Samma PK/CHECK/FK som Observation – arkivet har samma datakvalitet.

Vertikal: rader delas upp efter användning (aktiva vs arkiverade), inte kolumner. Proceduren ARKIVERAOBSERVATION flyttar raden hit.

Notera: proceduren tar bort kopplingarna i Rapporterat innan raden flyttas – arkivet sparar alltså inte vittnen. Det är ett medvetet designval i den här lösningen.

8. Person (rad 94–99)

94   CREATE TABLE Person(
95     PersonId CHAR(13) NOT NULL,
96     Namn VARCHAR(100) NOT NULL,
97     Kodnamn VARCHAR(50),
98     PRIMARY KEY (PersonId)
99   ) ENGINE=INNODB;
RadVad den gör
95CHAR(13) = fast längd, t.ex. 19850512-1234. Varför inte heltal? Bindestreck och inledande siffror ska bevaras exakt.
96Namn, obligatoriskt.
97Kodnamn får vara NULL – en person kan sakna kodnamn. Appen filtrerar på "SAKNAS".
98Primärnyckel på personnumret.

9. Rapporterat (rad 101–107): många-till-många

101  CREATE TABLE Rapporterat(
102    PersonId CHAR(13) NOT NULL,
103    ObsId INTEGER NOT NULL,
104    PRIMARY KEY (PersonId, ObsId),
105    FOREIGN KEY (PersonId) REFERENCES Person(PersonId),
106    FOREIGN KEY (ObsId) REFERENCES Observation(ObsId)
107  ) ENGINE=INNODB;
RadVad den gör
101Kopplingstabell: vilka personer som rapporterat/vittnat om vilka observationer.
102–103De två nycklarna till Person och Observation.
104Sammansatt PK: samma person kan inte kopplas till samma observation två gånger.
105–106FK till båda tabellerna – kopplingen kan inte peka på något som inte finns.

Varför: en person kan vittna om flera observationer och en observation kan ha flera vittnen → M:N. Apparna visar detta med LEFT JOIN; observationer utan vittnen får NULL.

10. ObservationLog (rad 109–117): loggtabell

109  /* LOGGTABELL: lagrar loggraden fran triggern LOGGOBSERVATION */
110  CREATE TABLE ObservationLog(
111    LogId INTEGER NOT NULL AUTO_INCREMENT,
112    Operation VARCHAR(10) NOT NULL,
113    Anvandare VARCHAR(100) NOT NULL,
114    ObsId INTEGER NOT NULL,
115    Tidpunkt DATETIME NOT NULL,
116    PRIMARY KEY (LogId)
117  ) ENGINE=INNODB;
RadVad den gör
110–111Loggtabell. AUTO_INCREMENT ger varje loggrad ett unikt id automatiskt.
112Vilken operation, t.ex. 'INS'.
113Vilken databasanvändare som gjorde det (USER()).
114Vilken observation det gäller.
115När det hände (NOW()).

Varför ingen FK på ObsId? Loggen ska finnas kvar även om observationen arkiveras eller tas bort. En FK skulle kunna blockera eller radera historiken.

12. Index (rad 169–177)

173  -- INDEX FOR QUERY SELECT * FROM Observation ORDER BY Datum DESC;
174  CREATE INDEX OBSDATUM ON Observation(Datum DESC) USING BTREE;
176  -- INDEX FOR QUERY SELECT * FROM Person ORDER BY Namn ASC;
177  CREATE INDEX PERSONNAMN ON Person(Namn ASC) USING BTREE;
RadVad den gör
174Index på Datum i fallande ordning – snabbar upp sortering på datum.
177Index på Namn – snabbar upp sortering på namn.

Varför: utan index måste databasen läsa hela tabellen och sortera. Index är som en innehållsförteckning. Kostnad: tar plats och gör inserts lite långsammare.

Notera: appens sökning LIKE '%namn%' med % först kan inte använda indexet fullt ut – indexet hjälper främst sortering och prefix/exakta sökningar.

13. Rättigheter (rad 179–214)

184  CREATE USER IF NOT EXISTS 'handlaggare_app'@'localhost' IDENTIFIED BY '';
187  GRANT EXECUTE ON a25milha.* TO 'handlaggare_app'@'localhost';
190  GRANT SELECT ON a25milha.GradBeskrivning TO 'handlaggare_app'@'localhost';
...  (fler SELECT)
202  GRANT SELECT, DELETE ON a25milha.Rapporterat TO 'handlaggare_app'@'localhost';
214  GRANT SELECT, INSERT, UPDATE, DELETE ON a25milha.Observation TO 'handlaggare_app'@'localhost';
RaderVad de gör
184Skapar en egen databasanvändare, bara åtkomlig från localhost.
187EXECUTE = får anropa lagrade procedurer i databasen.
190–211SELECT på kodtabeller, arkiv, handläggare, person, logg och agent – läsning räcker.
202SELECT, DELETE på Rapporterat – arkiveringsproceduren måste kunna ta bort kopplingar.
214Full CRUD på Observation – appen ska kunna söka, infoga, ändra och arkivera.

Minsta rättighet: användaren får bara det appen behöver – ingen DROP, ALTER eller rättighet på hela servern. Tio GRANT-rader uppfyller kravet på minst tre.

Anslutningarna i PHP/C# använder användaren dbkonstruktion; handlaggare_app är den separata användare som demonstrerar rättighetskravet.

14. Triggers (rad 220–239)

LOGGOBSERVATION – skriver logg

221  DELIMITER //
222  CREATE TRIGGER LOGGOBSERVATION AFTER INSERT ON Observation
223  FOR EACH ROW BEGIN
224    INSERT INTO ObservationLog(Operation, Anvandare, ObsId, Tidpunkt)
225    VALUES ('INS', USER(), NEW.ObsId, NOW());
226  END;
227  //
228  DELIMITER ;
RadVad den gör
221DELIMITER // byter tillfälligt sluttecken så att semikolon inuti BEGIN...END inte avslutar hela satsen.
222Skapar triggern. AFTER INSERT = körs automatiskt efter en insert på Observation. FOR EACH ROW = en gång per infogad rad.
224–225Skriver en ny rad i ObservationLog: operation INS, användare, den nya radens ObsId (NEW.ObsId) och tid.
226–228Avslutar triggern och återställer ; som sluttecken.
Säg: "Det här är en INSERT i triggern – den skriver en loggpost. NEW.ObsId läser bara ett fält från den nya raden; det finns ingen SELECT."

CHECKOBSGRAD – kontrollerar före insert

232  CREATE TRIGGER CHECKOBSGRAD BEFORE INSERT ON Observation
233  FOR EACH ROW BEGIN
234    IF (NEW.GradKod < 1 OR NEW.GradKod > 4) THEN
235      SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Narkontaktsgraden maste vara mellan 1 och 4.';
236    END IF;
237  END;
RadVad den gör
232BEFORE INSERT = körs innan raden sparas, så den kan stoppa den.
234Om den nya graden är utanför 1–4 …
235… avbryts inserten med ett eget felmeddelande (SIGNAL SQLSTATE '45000').

15. Procedurer (rad 241–260)

GETAVGSAKERHET – läser medelvärde

243  CREATE PROCEDURE GETAVGSAKERHET()
244  BEGIN
245    SELECT AVG(Sakerhet) AS MedelSakerhet FROM Observation;
246  END;

Returnerar en rad med medelvärdet av Sakerhet. Anropas med CALL GETAVGSAKERHET() i båda apparna. AS MedelSakerhet ger kolumnen ett namn.

ARKIVERAOBSERVATION – flyttar en rad

252  CREATE PROCEDURE ARKIVERAOBSERVATION(IN p_ObsId INTEGER)
253  BEGIN
254    DELETE FROM Rapporterat WHERE ObsId = p_ObsId;
255    INSERT INTO ARKIVERADObservation
256    SELECT * FROM Observation WHERE ObsId = p_ObsId;
257    DELETE FROM Observation WHERE ObsId = p_ObsId;
258  END;
RadVad den gör
252Tar en parameter IN = indata: vilket ObsId som ska arkiveras.
254Tar bort kopplingarna i Rapporterat först – annars blockeras borttagningen av FK.
255–256Kopierar raden till arkivtabellen. SELECT * fungerar eftersom båda tabellerna har samma kolumnordning.
257Tar bort raden från den aktiva tabellen.

Tre steg i ordning: kopplingar → arkiv → aktiv tabell. Anropas från apparna med CALL ARKIVERAOBSERVATION(?).

17. Self-test

1. Varför DROP DATABASE först?

För att filen ska kunna köras om från början utan att tabeller redan finns. All data raderas.

2. Vad betyder sammansatt primärnyckel i Agent?

Kombinationen AgentNamn + AgentNr är unik; ingen av kolumnerna behöver vara unik ensam.

3. Varför CHAR(1) för AgentNamn?

Det är en fast ett-teckens kod; CHAR ger exakt längd.

4. Vad kontrollerar CHECK (Lon ...)?

Att lönen ligger mellan 12 000 och 25 000.

5. Varför egen tabell för AgentKommentar?

Horisontell denormalisering: stor text flyttas ut så huvudtabellen blir liten och snabb.

6. Vad skiljer Handlaggare från Agent?

Handlaggare är en delmängd av Agent – bara de som har rollen handläggare finns i tabellen.

7. Varför UNIQUE på PlatsNamn?

Förhindrar två olika koder för samma platsnamn.

8. Vad är merge i Observation?

IncidentId/IncidentNamn och registrerare ligger direkt i tabellen i stället för i egna tabeller – färre joins.

9. Varför ingen FK på ObservationLog.ObsId?

Loggen ska överleva även om observationen arkiveras eller tas bort.

10. Varför DELETE Rapporterat först i proceduren?

FK från Rapporterat till Observation hindrar annars borttagningen av observationsraden.

11. Varför index på Datum?

Sorteringen ORDER BY Datum DESC blir snabbare än att läsa och sortera hela tabellen.

12. Vad gör DELIMITER //?

Byter sluttecken tillfälligt så att semikolon inuti BEGIN...END inte avslutar satsen för tidigt.

Ett block per dag räcker. Läs koden, täck förklaringen, säg den högt, skriv om raden ur minnet nästa dag.
