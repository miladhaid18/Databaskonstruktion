MUNTLIG REDOVISNING - PUNKTLISTA (IT429G HT26)

 Byggd pa: "Förtydligande frågor pa muntlig tentamen" + instruktionsfilen

Sa examineras du:

- 3 slumpvis valda fragor fran listan nedan + 1 personlig fraga
- Max 5 minuter per fraga (tar en delfraga > 5 min = underkand)
- Du visar appen pa wwwlab.webug.se och koden pa git.webug.se
- ENDAST dessa tva sidor. Ingen editor/Visual Studio.
- Du maste HITTA koden pa git och FORKLARA vad den gor.
- Examinationen utgar fran SENASTE COMMIT i det publika repot.
- Fungerar inte appen = ofullstandig.

FRAGORNA (exakt enligt kravlistorna):
DATABAS

D2 - LOGISK DESIGN: DATATYPER (forsta steget)

Repo: databaskonstruktion-assignment-1-startup
Visa: database.sql

- rad 10  AgentNamn CHAR(1)        fast kod, alltid 1 tecken
- rad 11  AgentNr INTEGER          heltal
- rad 12-13 Fornamn/Efternamn VARCHAR(50)
- rad 14  Lon INTEGER DEFAULT 13000
- rad 26  Kommentar VARCHAR(1024)  lang text
- rad 40  PlatsKod INTEGER
- rad 41  PlatsNamn VARCHAR(100)
- rad 48  Beskrivning VARCHAR(100)
- rad 54  ObsId INTEGER
- rad 55  Datum DATETIME           datum + tid
- rad 57  Sakerhet DECIMAL(5,2)    procent med 2 decimaler
- rad 59  IncidentNamn VARCHAR(100)
- rad 95  PersonId CHAR(13)        fast langd (personnummer)
- rad 111 LogId INTEGER AUTO_INCREMENT
- rad 112 Operation VARCHAR(10)

Sag sa har:
- "Minst tre olika datatyper anvands: CHAR, INTEGER, VARCHAR,
  DECIMAL och DATETIME."
- CHAR(1)/CHAR(13) for varden med fast langd (agentnamn, personnr)
- DECIMAL(5,2) for Sakerhet: undviker avrundningsfel som flyttal ger
- DATETIME for Datum: bade datum och klockslag
- AUTO_INCREMENT pa LogId: databasen skapar unikt loggnummer

D3 - LOGISK DESIGN: CONSTRAINTS (andra steget)

Repo: databaskonstruktion-assignment-1-startup
Visa: database.sql

PRIMARY KEY: rad 15, 27, 34, 42, 49, 63, 84, 98, 104, 116
FOREIGN KEY: rad 28, 35, 68, 69, 70, 89, 90, 91, 105, 106
CHECK:
- rad 17  CHECK (Lon >= 12000 AND Lon <= 25000)
- rad 19  CHECK (AgentNr > 0 AND AgentNr <= 99)
- rad 65  CHECK (GradKod >= 1 AND GradKod <= 4)
- rad 67  CHECK (Sakerhet >= 1.00 AND Sakerhet <= 114.00)
- rad 86, 88 samma CHECK i ARKIVERADObservation

- rad 41  PlatsNamn VARCHAR(100) NOT NULL UNIQUE

NOT NULL: bl.a. rad 10-14, 40-41, 54-62, 95-96

Sag sa har:
- "Constraints ar regler som databasen sjalv uppratter: PK, FK,

- CHECK hindrar ogiltig lon, agentnr, grad och sakerhet
- UNIQUE pa PlatsNamn hindrar dubbletter av platsnamn
- FK hindrar att en observation pekar pa en plats/grad/handlaggare
  som inte finns
- Varje CHECK har en enradig forklarande kommentar (kravet)

D4 - FYSISK DESIGN: DENORMALISERING (forsta steget)

Repo: databaskonstruktion-assignment-1-startup
Visa: database.sql

Definitioner (lararens kodexempel):
- MERGE          = sla ihop tabeller/kolumner till en tabell
- HORISONTELL    = lyft ut stora textkolumner som sallan las
- VERTIKAL       = dela upp rader efter anvandningsfrekvens
- KODIFIERING    = byt ut upprepad text mot en kod + kodtabell

I din databas:
- MERGE + KODIFIERING 1 & 2: Observation (rad 52-71)
  * IncidentId/IncidentNamn lagras direkt i varje observationsrad
    (ingen separat Incident-tabell) = merge
  * PlatsKod (rad 60, FK rad 69) mot Plats (rad 38-43) = kod 1
  * GradKod (rad 56, FK rad 70) mot GradBeskrivning (rad 45-50) = kod 2
- HORISONTELL: AgentKommentar (rad 22-29)
  * Kommentar VARCHAR(1024) lyfts ut till egen tabell med samma PK
  * vinst: stora texten las inte in vid vanliga Agent-fragor
- VERTIKAL: ARKIVERADObservation (rad 73-92)
  * aktiva observationer (Observation) och arkiverade
    (ARKIVERADObservation) hall isar
  * vinst: den aktiva tabellen blir mindre och snabbare

Sag sa har:
- "Kravet: merge + kodifiering minst 3 totalt (har: 1 merge + 2
  kodifieringar) och horisontell/vertikal minst 2 totalt (har 1+1)."
- Forflyttningen mellan aktivt/arkiv sker med proceduren
  ARKIVERAOBSERVATION (rad 252-258)

D5 - FYSISK DESIGN: INDEXERING (andra steget)

Repo: databaskonstruktion-assignment-1-startup
Visa: database.sql

- rad 173-174  CREATE INDEX OBSDATUM ON Observation(Datum DESC) USING BTREE;
  kommentar ovanfor visar query: SELECT * FROM Observation ORDER BY Datum DESC
- rad 176-177  CREATE INDEX PERSONNAMN ON Person(Namn ASC) USING BTREE;
  kommentar ovanfor visar query: SELECT * FROM Person ORDER BY Namn ASC

Sag sa har:
- "Index ar som en sorterad katalog som gor sokning/sortering snabbare."
- Bada ar BTREE (bra for likhet, intervall och ORDER BY)
- Indexen ar valda utifran vanliga queries som sorterar pa Datum/Namn
- PK far automatiskt index; dessa tva ar extra for sortering
- Kravet: minst 2 index, en enradig kommentar per index (uppfyllt)

D7 - FYSISK DESIGN: PROCEDURES / TRIGGERS (femte steget)

Repo: databaskonstruktion-assignment-1-startup
Visa: database.sql rad 218-260

Fyra objekt = fyra av lararens typer:
- rad 222-228  LOGGOBSERVATION (TRIGGER, AFTER INSERT)
  * loggning: skriver Operation='INS', USER(), NEW.ObsId, NOW()
    till ObservationLog (rad 110-117)
- rad 232-239  CHECKOBSGRAD (TRIGGER, BEFORE INSERT)
  * constraint: SIGNAL SQLSTATE '45000' om GradKod utanfor 1-4
- rad 243-248  GETAVGSAKERHET (PROCEDURE)
  * funktion: SELECT AVG(Sakerhet) FROM Observation
- rad 252-258  ARKIVERAOBSERVATION (PROCEDURE, IN p_ObsId)
  * materialisering/flytt i tre steg:
    rad 254  DELETE FROM Rapporterat WHERE ObsId = p_ObsId;
    rad 255-256  INSERT INTO ARKIVERADObservation
                 SELECT * FROM Observation WHERE ObsId = p_ObsId;
    rad 257  DELETE FROM Observation WHERE ObsId = p_ObsId;
  * Rapportarat raderas forst sa att FK inte blockerar flytten

Anvands i applikationerna:
- PHP: rad 85 CALL ARKIVERAOBSERVATION(?), rad 161 CALL GETAVGSAKERHET()
- .NET: ObservationModel.cs rad 96 CALL ARKIVERAOBSERVATION(@OBSID),
  PersonModel.cs rad 33 CALL GETAVGSAKERHET()

Sag sa har:
- "Trigger kor automatiskt vid INSERT; procedur anropas med CALL."
- Loggning och constraint kan inte glommas eller kringgas av appen
- Samma procedur anvands av bade PHP och .NET (= logiken pa ett stalle)
- Kravet: minst 4 objekt, minst 1 trigger + 1 procedur och minst
  2 typer (har: funktion, constraint, loggning, flytt = 4 typer)

PERSONLIG FRAGA - VALJ 2-3 ATT PRATA OM

1. Loggtriggern LOGGOBSERVATION (database.sql rad 222-228)
   - Automatisk revisionslogg i ObservationLog, kan inte glommas
2. CHECKOBSGRAD (rad 232-239)
   - Databasen stoppar ogiltig grad aven om appen har bugg
3. ARKIVERAOBSERVATION (rad 252-258)
   - Flytt aktiv -> arkiv i en procedur, anvands av bade PHP och .NET
4. Nastlad tabell med prev-variabel (PHP rad 182-212, .NET rad 26-52)
   - Grupperar detaljrader under ratt huvudrad
5. Dropdowns fran databasen + validering/TempData
   - Alla listor kommer fran Plats/Agent/Person; fel visas snyggt
