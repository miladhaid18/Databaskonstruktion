Del 1 – Databasimplementation

1Vilket påstående om merge är korrekt?Ett svar

a) Merge delar upp en tabell i två tabeller med samma primärnyckel.
b) Merge slår ihop två relaterade tabeller (1:1 eller 1:N) och eliminerar JOIN-frågor, men ökar redundansen.
c) Merge ersätter återkommande textsträngar med numeriska koder.
d) Merge delar upp rader i aktiva och arkiverade tabeller.
e) Merge kräver alltid en N:M-relation.

Del 4 – Flera korrekta svar

8Vilka påståenden om SQL-injection och skydd är korrekta?Flera svar

a) SQL-injection kan uppstå när användarinput klistras in direkt i en SQL-sträng.
b) Prepared statements med platshållare gör att input behandlas som data, inte som SQL-kod.
c) Stored procedures med parametrar och begränsade rättigheter kan minska risken för SQL-injection.
d) mysql_real_escape_string ensamt garanterar alltid full säkerhet.
e) Triggers är det primära skyddet mot SQL-injection.

9Vilka fel finns i denna C#-kod?Flera svar

public DataTable SearchCustomers(string name)
{
    MySqlConnection dbcon = new MySqlConnection(_connectionString);
    dbcon.Open();
    MySqlDataAdapter adapter =
        new MySqlDataAdapter("SELECT * FROM CUSTOMER WHERE name = @NAME;", dbcon);
    adapter.SelectCommand.Parameters.AddWithValue("@NAM", "%" + name + "%");
    DataSet ds = new DataSet();
    adapter.Fill(ds, "result");
    DataTable CustomerTable = ds.Tables["result"];
    dbcon.Close();
    return CustomerTable;
}
a) Parameternamnet i SQL (@NAME) matchar inte namnet i AddWithValue (@NAM).
b) = används i stället för LIKE, så %-jokertecknen i värdet fungerar inte.
c) MySqlDataAdapter kan inte fylla en DataSet.
d) AddWithValue får inte användas tillsammans med MySqlDataAdapter.
e) dbcon.Close() tömmer DataTable innan den returneras.
Motivering (30–50 ord):

Facit och modellmotiveringar

FrågaRätt svarModellmotivering (30–50 ord)
1b
Merge slår ihop två relaterade tabeller (1:1 eller 1:N) till en tabell, vilket eliminerar kostsamma JOIN-frågor och snabbar upp läsningar. I caset kan Spel och Utgivare slås ihop eftersom en utgivare har många spel. Nackdelen är ökad redundans och risk för inkonsistens.
a = vertikal split, c = kodifiering, d = horisontell split. Merge är inte reserverat för N:M – tvärtom passar det bäst för 1:1 och 1:N.
2d
Vertikal split delar upp en tabell efter kolumner: stora eller sällan använda fält flyttas till en egen tabell med samma primärnyckel. I caset kan informationOmMig flyttas från BadJB_medlemmar till MedlemInfo. Huvudtabellen blir mindre och snabbare, men frågor över båda tabellerna kräver JOIN.
a = horisontell split, b = merge, c = kodifiering, e = index.
3c
CHAR(12) ger fast längd och CHECK med REGEXP '^[0-9]{12}$' säkerställer exakt tolv siffror. NOT NULL gör värdet obligatoriskt och UNIQUE förhindrar dubbletter. INT(12) anger bara visningsbredd, och VARCHAR(12) tillåter kortare värden och bokstäver.
a = visningsbredd, ingen kontroll; b = tillåter bokstäver/blanksteg; d = variabel längd; e = decimaltal, inte exakt 12 siffror. CHECK kräver MySQL 8.0.16+; i äldre versioner kan en trigger med SIGNAL SQLSTATE '45000' användas.
4a
En trigger exekveras automatiskt av databasmotorn vid BEFORE eller AFTER INSERT, UPDATE och DELETE, medan en stored procedure anropas explicit med CALL. I caset kan en trigger validera Svårighet vid insert, och en procedur beräkna statistik som applikationen anropar.
b = omvänd ordning; c = bara triggers körs automatiskt; d = triggers kan validera; e = procedurer kan ta parametrar.
5e
GET skickar data i URL:en och passar för sökningar som ska kunna bokmärkas, medan POST skickar data i request-body och passar för ändringar och känslig information. I caset kan spelsökning använda GET och registrering av ett nytt spel använda POST.
a = omvänd; b = falskt; c = falskt; d = falskt (GET kan skicka text).
6b
FETCH_ASSOC returnerar rader med kolumnnamn som nycklar, FETCH_NUM med numeriska index och FETCH_BOTH med båda. FETCH_ASSOC är minnessnålt och tydligt. Prepared statements skickar fråga och värden separat, så input behandlas som data och inte som SQL-kod.
a = fel om FETCH_BOTH; c = bindParam binder by reference; d = prepared statements klistrar inte in värden; e = execute() behöver inga argument när värden bundits.
7c
Requesten går via routingen till controllern, som anropar modellen. Modellen frågar databasen och returnerar en DataTable, som controllern lägger i ViewBag och skickar till vyn. Vyn renderar HTML. Ansvaren är separerade: controller styr flödet, modell data och vy presentation.
a, b, d och e blandar ansvaren: vyn ska inte fråga databasen, modellen ska inte rendera HTML och controllern är inte en del av databasen.
8a, b, c
SQL-injection uppstår när input klistras in direkt i SQL. Prepared statements med platshållare skickar fråga och värden separat, så input alltid blir data. Stored procedures med parametrar och begränsade rättigheter minskar också risken. Triggers är inte ett skydd, och escape-funktioner ensamma garanterar inte säkerhet.
d = escape ensamt är inte fullgott skydd; e = triggers är inte primärt skydd.
9a, b
Två fel: parameternamnet @NAM matchar inte @NAME i SQL-frågan, och WHERE använder = i stället för LIKE, så %-jokertecknen inte fungerar. DataSet, DataTable och AddWithValue är korrekt använda. Rätt parameter och LIKE krävs för delmatchning.
c, d och e är felaktiga påståenden: adaptern kan fylla en DataSet, AddWithValue fungerar och Close() tömmer inte tabellen.
10a, b, c
Tre fel: UPDATE saknar WHERE och skulle uppdatera alla fakturarader, parametern customernumber binds men finns inte i SQL-strängen, och superglobalen $POST är felstavad; den ska vara $_POST. FROM behövs inte i UPDATE, och execute() behöver inga argument när bindParam använts.
d och e är inte fel: UPDATE har ingen FROM-sats, och bundna värden skickas inte till execute().
